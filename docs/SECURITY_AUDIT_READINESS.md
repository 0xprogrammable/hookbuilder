# Security and audit readiness

This is the review entry point for Builder release `0.4.0`. It records evidence and remaining gates; it is not an
independent audit report, a deployment approval, or a claim that arbitrary projects generated by the skill are safe.

## Review surfaces

| Surface | Canonical path | Primary risk |
| --- | --- | --- |
| Agent operating contract | `skills/programmable-v4-hook-builder/SKILL.md` | unsafe authority, hidden action or overclaim |
| Protocol and platform policy | `skills/programmable-v4-hook-builder/references/` | stale or contradictory rules |
| Composition system | `skills/programmable-v4-hook-builder/assets/starter-catalog/` | unsafe defaults or template gatekeeping |
| Submission validator | `skills/programmable-v4-hook-builder/scripts/submission-core.mjs` | false acceptance, false rejection or evidence inflation |
| GitHub transport | `skills/programmable-v4-hook-builder/scripts/github-*.mjs` | source confusion, repository substitution or unintended write |
| Fee reference kernel | `skills/programmable-v4-hook-builder/assets/reference-kernels/programmable-volume-fee-v1/` | value loss, fee bypass or authority failure |
| Host packaging | `config/plugin.json`, generated manifests and release artifacts | policy duplication or supply-chain drift |

## High-value invariants

- PoolManager callback and unlock authentication is immutable.
- One hook instance binds atomically to one canonical pool and exact permission bits.
- Programmable's inclusive 10 bps liability is computed from executed gross quote-side volume and survives swap
  fragmentation through independent cumulative remainders.
- Only `0x4957f49620AFf3Adbbe8195a4f633E49cc93376c` can initiate Programmable fee claims; project ownership and the separate
  platform admin cannot claim or redirect them.
- Return deltas must be backed, bounded and conserved; every successful unlock finishes with zero PoolManager deltas.
- Exact-output, partial-fill, native/ERC-20 settlement, all four swap quadrants, claim separation and hostile pool keys
  have executable coverage in the reference candidate.
- The agent cannot convert its own local check into maintainer approval, deployment, provider support or public launch.

## Known remaining gates

- No independent security audit has been completed for this release or the reference kernel.
- No Echidna campaign, symbolic execution, formal proof, mainnet-fork campaign or production gas envelope is claimed.
- No hook from this repository is deployed by the release process; there is no bytecode/source/runtime receipt.
- Model-backed prompt evaluations have not been executed for this candidate.
- External apps, games, services, indexers, wallets, oracles, keepers and custom builder code require their own threat
  models and evidence. Passing the Builder cannot inherit evidence across those boundaries.
- Protocol, SDK, chain and provider state can drift after the pinned source snapshot and must be refreshed in a new
  release rather than silently changing an old tag.

## Suggested independent review order

1. Reproduce the release checksums, file manifest and SPDX SBOM from the exact tag.
2. Review the fee policy, kernel value-flow diagram, permission bits, rounding and claim state before individual lines.
3. Trace every external action and authority transition in the agent and GitHub application workflows.
4. Challenge the semantic validator with unknown architectures, malicious repositories and evidence-confusion cases.
5. Re-run static, fuzz, invariant, fork and model-backed campaigns independently.
6. Record findings against an exact commit and distinguish Builder defects from defects in generated projects.
