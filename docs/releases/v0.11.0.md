# Programmable v4 Builder v0.11.0

This feature release makes the normal Applicant journey one persistent command while retaining the exact protected
Application V3.1 transport and its existing authority boundaries.

## One Applicant command

- `submit-project <repository-root>` discovers exactly one tracked Submission V2 subject or one closed tracked pointer.
- It validates the project, creates or resumes one private outside-source workspace, prepares the closed Application
  package when every exact input exists, and returns one read-only Draft plan.
- Reinvoking the same command reads status or resumes an interrupted mutation. Only the exact freshly recomputed
  confirmation digest permits one create or update attempt; ambiguous writes use GET-only reconciliation.
- Default output contains at most three six-field diagnostics with one safe next command. Internal phase commands remain
  available under `advanced` and `legacy`, not in the normal help surface.

## Protected compatibility and portable validator

- The command binds the exact public `0xprogrammable/submit-launch:main` repository identity, commit, tree, Application
  schema bytes, and Applicant compatibility contract before creating a workspace or attempting a GitHub write.
- Released central bases without the new compatibility document remain usable only through the exact closed
  active-contract and Application-schema fallback. A changing or mismatched base fails closed with zero writes.
- The Builder can generate and verify one bounded minimal Applicant validator package. Descriptor-bound reads,
  no-follow checks, pre/post identity checks, per-file hashes, aggregate bounds, and a deterministic closure receipt
  protect the package before central reuse.
- The reviewed portable Skill ceiling moves from 620 files and 8,750,000 bytes to 630 files and 8,900,000 bytes to
  accommodate the separated compatibility, diagnostics, and one-command journey modules without relaxing per-module
  size or complexity limits.

## Evidence boundary

The command does not invent source, review material, security evidence, prototype state, trade capability, Fee V2
selection, test results, or repository identities. A valid proposal may create only an unreviewed Applicant Draft.
Review, acceptance, approval, deployment, registration, availability, routing, signing, funds, and launch authority
remain false and separate.

At packaging time, the public Submit Launch `v1.6.3` active contract remains the exact released compatibility fallback.
The compact validator and canonical compatibility manifest become central public behavior only after their own protected
Submit Launch merge, release, and readback. The bundled `publicationStateVerified: false` status is not proof that
Hookbuilder `v0.11.0` is public. Protected CI, the immutable tag and assets, attestations, public API visibility, fresh
installation, and one real Draft-only canary must be verified independently after publication.
