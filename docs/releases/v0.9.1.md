# Programmable v4 Builder v0.9.1

This patch fixes the community-reported case where the Builder designed a valid custom Uniswap v4 architecture and
then refused to implement it because the design did not match the frozen `programmable-volume-fee-v2` profile.

## Custom tradable projects are buildable

- A technically viable custom tradable project can now provide complete Foundry source plus behavioral, fuzz,
  invariant, and deployment tests without selecting any bundled reference profile.
- Templates and reference kernels remain optional Legos. A missing catalog entry or profile never justifies refusing
  source generation.
- The exact Mizu regression covers a directional, size-sensitive, decaying dynamic LP fee, standard-transfer token,
  canonical Uniswap v4 pool, and untaxed liquidity modifications. It now produces a custom local source-and-test plan
  instead of `INTEGRATION_PENDING` or `EXTERNAL_BLOCKED`.
- Exact intent-bound legacy replay may still select `programmable-volume-fee-v2`; the Builder never infers or silently
  substitutes that profile.

## No release timer

- There is no minimum interval between Builder releases. A new exact candidate may move through review, required CI,
  owner authority, immutable artifacts, and publication immediately after an earlier release.
- Release history remains bound for monotonic version checks, provenance, and exact public identity, but it cannot
  calculate a waiting period or block a release because too little time has elapsed.
- Security hotfixes use the same timing rule as normal releases; severity grants no special timing bypass. Existing
  review, authority, reproducibility, immutable-tag, artifact, and post-publication verification gates remain intact.

## Policy and execution boundaries

The current central Submit a Launch policy remains the only Programmable launch-requirements authority and is evaluated
for submission. It is not a source-code allowlist. If the policy is unavailable, the Builder records
`POLICY_UNRESOLVED` and may continue local source authoring while blocking submission, approval, and launch.

The portable materializer reads bounded regular source/test files, writes a clean local Foundry repository, and emits
exact source, test, plan, commit, tree, and evidence identities. It does not execute candidate code, access the network,
approve, audit, deploy, publish, register, sign, move funds, submit, or launch anything. Execution and completion still
require separately authenticated sandbox evidence.

## Verification boundary

The exact candidate passed the complete local repository verifier, the focused custom-tradable/Mizu and no-release-
interval regressions, plugin source-byte verification, Contract Registry verification, size gates, deterministic eval
structure, and the Agent Skills publication dry-run. Provider/model evaluation was not run for this patch; the
regressions are deterministic implementation evidence, not a universal model-quality claim.

Generator-backed local inventories cover 331 production JavaScript modules and a Contract Registry of 51 portable
contracts with 26 validator closures, 1,037 transitive module bindings, and 178 distinct modules. The portable package
contains at most 686 reviewed files. The legacy Fee V2 reference kernel retains 54 unit, one fuzz and three invariant
test functions, and the repository retains 9 local test source files under `evals/tests/*.test.mjs`. The bundled state retains
`publicationStateVerified: false`; source, branch, or local test evidence does not prove a public v0.9.1 tag or release.

## Authority boundary

Local materialization remains `NOT_SUBMITTED` and `NOT_APPROVED`. Policy satisfaction and passing tests are not an
audit or automatic approval. Protected Submit a Launch and Website services retain independent review, acceptance,
deployment, routing, discovery, signing, real-funds, and launch authority.
