# Programmable v4 Builder v0.9.0

This release closes deterministic knowledge routing over the complete canonical catalog, activates one confirmed
specialist reference at a time, adds a bounded non-completion repair path, and strengthens journey evidence. It does
not change Programmable launch requirements, existing project-state schemas or completion semantics, review outcomes,
or any audit, approval, deployment, routing, funds, signing, or launch authority.

## Complete catalog knowledge routing

- Every canonical catalog capability and project surface must occur in at least one explicit knowledge route.
- Missing catalog coverage fails closed with `KNOWLEDGE_ROUTING_INVALID` instead of silently omitting specialist
  context.
- Newly closed capabilities use explicit applicable existing specialist references.
- Genuinely new owner-defined capabilities remain eligible and continue to architecture review.
- Eval context profiles come from one closed registry. Generic profiles cannot construct or preload unregistered,
  archival, or exact legacy Fee V2 references; `legacy-fee-v2` is reserved for
  `transparent-high-fee-open-world`.

This is deterministic routing coverage for the exact packaged catalog and route bytes. It is not evidence of broader
model intelligence, model-provider parity, audit completion, or production behavior.

## Confirmed specialist activation

The model-facing path starts with `context --brief`, binds its exact `profileDigest`, and activates only after an exact
capability or surface is confirmed. Activation is delta-only, promotes at most one specialist reference, preserves
split-review holds, and rejects missing, stale, family-level, or caller-mutated authority. The frozen Fee V2 chapter is
both filtered from normal candidates and forbidden in activation rules.

## Hash-bound repair diagnosis

The additive `project-repair-attempt-v1` contract records one ordered passed prefix, exactly one failed or
tooling-blocked root command, and the exact suppressed suffix. It binds the request, source, plan, command, runtime,
policy, output, signature, attempt chain, and external-effects boundary. `project diagnose` is read-only, permits an
initial attempt plus at most two repairs, and allows only one request-global blind retry for timeout or signal. Within
one chain, branch, command plan, and output path cannot change; `tooling-blocked` requires identical request bytes.

The existing all-pass sandbox receipt, project-state schema, and completion semantics are unchanged. A repair attempt
is always `NOT_COMPLETION` and `NOT_APPROVAL`; a later failed attempt in the supplied diagnosis chain cannot omit or
replace an earlier failure. The portable diagnosis treats the signature and signer as unverified until an independent
trust root authenticates them. The exact Repair cold brief is 1,391 bytes and 2,514 estimated tokens with only the
1,930-byte repair loop in `loadNow`. This is a bounded diagnostic path, not autonomous proof that a semantic root cause
was found or fixed.

## Journey and reference evidence

Repository E2E adapters now return the structured Builder response and an activation receipt for every reported
reference path, SHA-256, byte count, phase, reason, and decision. The harness validates those bytes against the exact
installed Skill, binds the provider response hash, derives the structured-question count, and sends the response and
activation receipt to the judge as untrusted data.

The daily sentinel reuses five existing public cases and adds five positive plus five negative trigger prompts. It is
a small selection manifest, not another benchmark system. No provider/model run was performed, and same-UID process
isolation and closed host activation remain `PROCESS_ISOLATION_UNPROVEN` until trusted external host and sandbox
evidence exists.

## Optional Project Compiler brief view

`--brief` is available for `validate`, `validate-output`, `preflight`, and `require-output`. It preserves the command
exit status, result status, full canonical report SHA-256, finding counts, `canonicalOutput`, and `evidenceBoundary`.
It omits the exhaustive inventory and finding arrays, shows at most three distinct finding-code groups, and tells the
caller to rerun the same command without `--brief` for the complete canonical JSON.

The complete report remains the default and the authority for its own bytes. The brief object is a presentation-only
projection bound back to that report; it is not a new project schema, approval record, audit result, or authority
contract. Complete brief stdout, including its trailing newline, is capped at 2,499 bytes; over-budget finding-group
details fall back to an explicit bounded summary rather than changing the underlying report.

## Authority boundary

Policy satisfaction and local validation are not an audit or automatic approval. The central `production-launch`
profile remains disabled. Protected Submit a Launch and Website services retain their independent decisions. Nothing
in this release grants review, acceptance, eligibility, deployment, routing, discovery, real-funds, signing, or launch
authority.
