# Programmable v4 Builder v0.5.0

This is the release where Programmable's creation path becomes three deliberately separate products:

1. **Builder:** the portable agent skill turns a plain-language idea into a checked project and exact application.
2. **Registry:** the public ledger records applications, review history, accepted revisions, status, and discovery.
3. **Platform:** the private Admin and launch path independently reviews evidence and authorizes a specific accepted
   revision. It never trusts the Builder to approve itself.

Builders keep their complete source in their own public GitHub repositories. New Application V3 packages bind every
primary and companion repository by immutable identity, commit, tree and inline or manifest source closure, then target
the dedicated [`programmable-registry`](https://github.com/0xprogrammable/programmable-registry). The platform remains
responsible for independent Admin review, deployment integration and launch execution.

## What changed

- Made context selection self-discovering: help lists the exact capability, surface and pack ids, while internal
  route-family names return typed non-adverse guidance and genuinely new owner-defined behavior stays eligible.
- Made the context budget include the exact canonical JSON response that an agent receives, and replaced raw
  missing-file failures with actionable Application V3 guidance when status is invoked on a Submission V2 package.
- Added live project discovery with `discover list`, `search`, `show`, and `compare`.
- Bound every live read to the Registry's fixed numeric repository id, exact commit, tree, canonical index, and selected
  record digest.
- Added a content-hash-verified offline snapshot that is never used silently and always reports its capture time,
  Registry digest, exact public commit, and root tree. Its portable raw-Git receipt binds the required paths and
  commit/tree/blob bytes without a checkout or network. The baseline must already be public before the Builder vendors
  it; later Registry changes enter a later Builder release rather than creating a self-referential release cycle.
- Kept similarity informational: a close match cannot reject an idea, and no match cannot prove novelty.
- Moved new applications to the dedicated Registry while preserving all existing v0.4.0 review threads.
- Added intent-first Open-World V2 packages, layered security evidence and Fee V2's exact inclusive 10 bps entitlement
  across declared canonical execution scopes without treating templates as product limits.
- Added GitHub-only Application V3 with multi-repository inline/manifest source closure, staged post-commit security,
  canonical decimal-string chain ids/revisions, and derived fee applicability: proposals are unresolved, canonical-scope
  prototypes bind a real instance, and exact zero-scope prototypes remain N/A without fabricated fee evidence.
- Split Application V3 preparation into GET-only revision/lineage derivation and a zero-network full-package build, with
  explicit historical-object replay for changed or removed repositories and no manual revision fields.
- Added bounded duplicate-key-safe raw JSON handling before privacy, integrity and semantic checks across current
  application, manifest, migration and launch paths.
- Added non-executing reconstruction of bounded static JavaScript public copy so literal joins, additions and templates
  cannot split forbidden safety, audit, endorsement or live-status claims; genuinely dynamic copy stays human-reviewed,
  while parser or resource-bound incompleteness becomes a tooling blocker rather than a pass.
- Extended output containment through recursive external Git alternate object stores, with cycle-safe bounds and
  fail-closed initial handling plus root-snapshot revalidation before staging and atomic rename.
- Added exact v0.4.0 template-catalog, definition, commit, and skill-tree receipts for future migrations.
- Preserved historical Submission V1/1.6.0 compatibility while routing new projects through Submission V2, Fee V2 and
  a deterministic fail-closed Launch Bundle V2 candidate for the Admin handoff.
- Added an explicit accepted-project update lifecycle. New bytes remain a pending update while the old exact accepted
  release stays launch-bound; a prior approval can never silently move to a new commit.
- Added a bounded exact configuration plan for post-acceptance ABI calls and storage reads. The separate Admin path must
  replay those expectations independently at one finalized canonical block before any signing decision.
- Kept the exact Agent Skills package name inside the versioned release archive so extracted artifacts verify directly,
  with separate repository-tree and portable-skill-tree receipts.
- Added a local release rehearsal that verifies the complete repository, Agent Skills publication shape, ordinary and
  unknown-idea routing, both reference kernels with explicit high-confidence fuzz and invariant settings plus pinned
  Slither, clean Codex, Claude Code and GitHub Copilot installations, extracted package integrity, two byte-identical
  artifact builds, both lockfiles in the SPDX SBOM, and checksums without publishing anything.

## Unchanged product rules

- Templates are accelerators, never a list of permitted products.
- Every application may describe a new hook, token, game, app, service, keeper, indexer, or multi-repository system.
- Unknown designs stay eligible and move to architecture review. Novelty alone is never a security verdict.
- Every `programmable-canonical` execution scope still owes the mandatory inclusive 10 bps Programmable share to the
  immutable claim owner. Exact zero-scope projects remain `not-applicable` and create no fake market or fee instance.
- A local pass is not an audit, approval, deployment, provider guarantee, public launch, or Uniswap endorsement.

## What a builder can do

Give the skill to a compatible coding agent and describe the product in ordinary language. It can route the minimum
relevant knowledge for Uniswap v4 or non-v4 surfaces, search the public project archive, compose reusable planning
foundations, preserve unfamiliar mechanics, build or repair the project, run applicable checks, bind exact public GitHub
source, prepare the application, submit only after explicit confirmation, and report when it is waiting for review.

The skill cannot approve itself, guarantee safety, sign, deploy, spend funds, or turn a local result into a live launch.
Registry acceptance, launch preparation, Admin authorization, deployment, indexing and public availability remain
separate evidence states.

## Upgrade note

Applications prepared with v0.4.0 stay bound to their existing `0xprogrammable/programmable` pull requests and should
continue with the pinned v0.4.0 status/update client. Newly prepared v0.5.0 applications target
`0xprogrammable/programmable-registry`.

## Verify

The release is eligible for publication only after the exact tag, commit, tree, checksums, SBOM, release manifest,
fresh-host canaries, public CI, release cadence, Registry intake activation, and owner-controlled release action are
verified. The GitHub release assets are the canonical receipts for those final bytes.

The local rehearsal command is:

```bash
npm run release:candidate -- \
  --tag v0.5.0 \
  --output-dir /absolute/path/to/programmable-v4-builder-v0.5.0-candidate
```
