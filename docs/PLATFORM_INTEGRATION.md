# Programmable platform boundary

This repository owns the Builder. It does not contain the live website, admin panel, database, deployment keys, provider
accounts or production indexer.

## Current builder journey

1. A builder uses any compatible coding agent with the pinned skill.
2. The agent turns an idea into a materialized plan and checked project in the builder's repository.
3. The builder publishes one exact public GitHub revision.
4. `prepare-pr` creates a bounded six-file application record and copy-ready draft pull-request body.
5. After an exact two-step external-write confirmation, the client may open or update the draft application PR.
6. Read-only status reports submitted, checks running, changes requested, waiting for review, review record merged, or
   closed.
7. Programmable maintainers review the exact revision and evidence in GitHub.

The application pull request is the transport and review thread. It is not self-approval, deployment authorization or a
wallet-connected platform account.

## Runtime and provider states

Public application eligibility is broad across JavaScript-safe EVM chains. The current documented Programmable custom
launch integration is Ethereum Mainnet-only. Other chains and new architecture families may be reviewed, but remain
blocked from a launch claim until the platform has an exact integration release, deployments, runtime verification,
indexing, monitoring and required provider evidence.

Provider state is recorded independently for discovery, metadata, charting, quoting, simulation and execution. No
single aggregate support flag may turn one observation into every other capability.

## Future platform consumption

The platform should consume this standalone repository by an immutable release tag or full commit and verify the skill
tree digest. Platform adapters may display status or call documented commands, but may not fork the fee policy, rewrite
readiness, weaken review gates, invent provider state, or auto-approve a submission.

An eventual connected application service and admin panel should project the same versioned application identity and
evidence ledger. Migration from GitHub PR transport requires an explicit versioned contract; it must not silently change
old applications or make the public Builder depend on a private service.
